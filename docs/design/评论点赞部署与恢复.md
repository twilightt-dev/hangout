# 评论点赞部署与恢复

本流程针对已确认的 Redis 关系事实来源、MySQL 计数投影方案。源码不会自动执行迁移或历史核对。任何实际历史数据修改、Redis 恢复写入和批量修复，必须先列出目标、精确命令及影响，再按 AGENTS.md 等待确认。

## 部署顺序

| 步骤 | 操作与验收 |
|---|---|
| 1 | 保留 MySQL 与 Redis 可恢复备份，核对 Redis AOF/RDB、备份周期和恢复演练；无独立关系历史日志 |
| 2 | 评估并执行 `backend/service/src/main/resources/db/migrations/20261014_comment_like.sql`，新增三列；迁移默认代次 0，不更改任何历史 liked |
| 3 | 部署九模块构建的 start.jar 和前端构建；新评论写入代次 1、版本 0、初始化标记 false |
| 4 | 首次访问新评论时，基础设施锁定该评论数据库行，初始化空 Redis 元数据并提交初始化标记；完成提交后才允许切换 |
| 5 | 验证登录切换、游客浏览、Redis 不可用时状态未知、后台投影同步及告警；只对审核过的历史评论逐条启用 |

迁移 DDL 不是可重复执行脚本。先查 INFORMATION_SCHEMA 确认尚无这些列；不要执行包含 DROP 的完整 hmdp.sql 来升级现有环境。全新数据库也需要执行此增量 DDL。Redis 正常负载下每秒限量同步 100 条，投影目标为几秒内可见；故障时没有硬实时保证。

应用配置通过环境或启动参数设置：`comment-like.write.enabled=false` 可暂停点赞 POST；`comment-like.sync.enabled=false` 可暂停同步，`comment-like.sync.delay-ms` 默认 1000。备份恢复操作需停止全部应用实例，避免 GET 初始化、在途 POST 和已发出同步继续操作；仅修改一个实例的配置不足以形成恢复屏障。

## 存储协议

| 存储 | 内容 |
|---|---|
| MySQL `liked` | unsigned INT 原字段；领域读模型与新 DO 使用 long/Long 覆盖完整数值范围 |
| `like_epoch` | 0 未核对停用，正数为已启用恢复代次 |
| `like_version` | 该代次已提交的计数版本 |
| `like_initialized` | 已在持久化行锁保护下完成 Redis 初始化。即使计数尚为 0，也不能因为 Redis 缺失而再次创建 |
| Redis `{comment:likes:P}:ID:users` | 用户 ID Set；P=评论 ID 对 4 取模，不过期 |
| Redis `{comment:likes:P}:ID:meta` | Hash：epoch、version、count；count 用于检测正数量关系 Set 意外丢失或损坏 |
| Redis `{comment:likes:P}:pending` | 待同步 ZSET：member 为评论 ID，score 为可尝试时间（毫秒）；与该分区所有关系键共用槽 |

切换、版本递增、数量和标记由同槽 Lua 原子修改。Lua 运行时错误不具备数据库式自动回滚，因此切换脚本先检查键类型、版本整数格式和关系数量，再进行写入。关系及元数据缺失、损坏或代次不符均暂停，不当作未点赞。Redis 应使用可靠持久化和备份，并避免对这些事实键设置 TTL 或采用会主动淘汰它们的内存策略。

点赞仓储复制现有 Lettuce 的连接地址、凭据、SSL 和超时配置，建立独立、非共享连接，关闭断线自动命令重放并拒绝断线命令；读取走主节点。新的请求可以建立新连接恢复访问，不更改遗留业务连接。隔离故障代理已验证“命令执行后丢失响应”返回不可用，后续读取看到真实已赞，切换只执行一次。此配置每次建立连接，实际容量与 TLS 连接开销需在部署时评估；不承诺第一版高吞吐。

同步以绝对数量写 MySQL，独立事务提交成功后才调用版本条件 ACK。旧版本只能被认定为已处理，不能覆盖新结果；不同代次和停用记录被拒绝并退避保留。ACK/退避仅在 Redis 代次和版本仍匹配时生效，新操作不会被旧任务清理或延后。

## 历史核对与启用

先以只读方式导出逐条清单：评论 ID、博客 ID、父级/状态、MySQL 数量/代次/版本/标记、Redis 关系数量、元数据和备份来源。数量相同不等于已证明用户集合正确，需要明确关系来源。

| 核对结果 | 处理 |
|---|---|
| NULL/0、Redis 无关系且无已用元数据 | 确认无历史关系后，可逐条将代次启用为 1；版本 0、初始化标记 false，允许首次空初始化 |
| 非零数量、无对应关系 | 保持代次 0、原数量和关系备查；按钮禁用，另行确定修复方案，不自动归零 |
| 有可信关系但与投影不符，或存在旧元数据 | 保持停用；审核实际用户关系，按下述恢复步骤启用更高代次并重建标记，不直接设 initialized=false |
| 来源不明或备份全部丢失 | 继续暂停；MySQL 数量无法恢复哪些用户点过赞 |

任何启用语句必须限定经审核的单条 ID 和预期旧代次，检查受影响行数等于 1；不能使用无 WHERE 的批量启用。启用前还要核实它是可见一级评论。未核对评论可继续展示原数量及“点赞状态暂不可用”。

## 备份恢复

1. 停止所有实例，保存当前数据和待同步记录，恢复可信备份。核对关系完整性及允许丢失的备份之后变更，记录每条评论审核数量与新代次。
2. 新代次必须大于 MySQL 当前代次和 Redis 旧代次。不要复用回退后的版本，不能只把 like_version 归零。
3. 离线执行资源 `backend/infrastructure/src/main/resources/lua/comment-like-recover.lua`。KEYS 按上表提供该评论的 users/meta/pending；ARGV 为预期 Redis 代次（无元数据用 missing）、旧 MySQL 代次、新代次、审核数量、评论 ID。脚本校验预期代次与 SCARD，再原子设置新代次、版本 1、数量和待同步标记。返回 -1 表示未通过检查，停止该条处理。
4. 对同一条已审核记录，按预期旧代次条件将 MySQL 设置为新代次、版本 0、初始化标记 true，保留旧 liked 等待投影；检查恰好更新一行。这里的版本 0 是受控新代次初始值，不是普通回退。Redis 脚本已成功但 SQL 未成功时，继续保持所有实例停止，先修复此步骤，不能提前放开请求。
5. 全部已批准记录 Redis/MySQL 代次匹配后启动同步，确认新代次投影已提交且待同步记录被 ACK，再恢复点赞流量。未批准或来源不明的记录保持代次 0。

脚本仅作为受控工具提供，应用没有管理 HTTP 入口或自动扫描恢复逻辑。脚本校验不替代人工审批用户集合，也不能找回未备份的关系。

## 验证范围

领域/应用/HTTP、H2 事务与条件 SQL、真实隔离 Redis Lua 及组合适配器均有自动测试。Redis 测试要求显式开关 `-DcommentLikeRedisTest=true` 与专用端口 `-DcommentLikeRedisPort=18643`，禁止默认 6379；测试随机命名空间不连接生产配置。生产 MySQL 锁、Redis Cluster 部署、备份策略和完整应用生命周期仍需在实际隔离部署中验证。
