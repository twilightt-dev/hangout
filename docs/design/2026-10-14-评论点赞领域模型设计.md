# 评论点赞领域模型设计

状态：已确认并完成源码实现。2026-10-14 用户审阅确认设计后进入实施；数据库迁移及真实历史数据修复未执行。

## 已确认的业务范围

| 项目 | 规则 |
|---|---|
| 对象 | 现有一级评论，parentId=0，status=0 或 NULL |
| 权限 | 登录用户可操作，允许自赞；身份来自服务端 |
| 行为 | 每次点击切换；已赞则取消，未赞则点赞 |
| 非法目标 | 不存在、被举报、隐藏或回复评论拒绝切换，已有关系保留 |
| 展示 | 评论列表展示点赞数、当前用户状态；游客看到未选中按钮，点击引导登录 |
| 不包含 | 回复、排行榜、通知、点赞用户列表 |
| 关系存储 | Redis 为事实来源，关系和待同步标记原子写入 |
| 计数存储 | MySQL 统计投影，允许短暂延迟，由后台自动校正 |
| 请求恢复 | 前端防连点，不自动重发；出错后重新读取状态再允许操作 |
| Redis 故障 | 评论与 MySQL 数量可展示，登录用户状态为未知，按钮禁用并可重试 |
| 数据恢复 | Redis 持久化和备份；第一版无独立关系历史日志 |
| 历史数据 | 启用前核对；非零数量缺少关系时暂停该评论点赞，单独处理；NULL 且无关系视为 0 |

状态切换不是幂等接口。前端防连点不是后端并发保证；两个终端分别发出的请求是两次操作。第一版不承诺网络超时后重发同一次请求仍只执行一次。

## 方案比较

| 模型 | 作用与代价 |
|---|---|
| 评论实体＋独立单用户点赞关系模型（已采用） | 评论管理身份和资格，关系模型管理一个用户的状态；不加载全体点赞用户，适合当前 Redis 存储选择 |
| 评论聚合内部维护全部点赞用户 | 可以直接管理集合，但对象大小随点赞人数增长；加载与保存大集合不适合现有 Redis Set 的局部操作 |
| 仅在应用 Service 中判断并调用 Redis/MySQL | 实现短，但评论资格与状态规则继续散落在流程中，不利于本次领域建模目标 |

## 类型及边界

| 类型 | 角色 | 负责范围 |
|---|---|---|
| Comment | 实体，作为评论自身的聚合根 | 自身 ID、博客 ID、作者 ID、CommentContent、parentId、answerId、状态；检查可见一级评论资格 |
| CommentContent | 值对象 | 继续维护 trim、非空及长度规则 |
| CommentLikeId | 值对象 | commentId＋userId 的自然身份，区分一个用户对一条评论的关系 |
| CommentLike | 小型关系实体，独立于评论聚合 | 单个用户当前是否已赞；从状态快照计算切换，不持有 Redis、Mapper 或全部点赞用户 |
| CommentLikeChange | 值对象 | 一次计划中的状态迁移，包含关系身份、原状态、目标状态 |
| CommentRuleViolation | 业务异常 | 非法 ID、评论不允许点赞等规则拒绝；技术故障不转换成规则错误 |

CommentLike 的身份可以跨取消与再次点赞延续；Redis 只保存有效成员，不要求为取消后的关系另建数据库记录。单用户关系模型是此次设计选择，不是每个点赞功能必须建立的类型。

Comment 不把 liked 当作自己的可直接加减属性。Redis 关系是事实来源，MySQL liked 是统计投影：让 comment.likeCount++ 后保存会与并发和最终一致性冲突。点赞数继续进入查询与操作结果，不作为判断一个用户是否已点赞的依据。

恢复已有 Comment 时加载真实 ID、父评论及状态，不能使用创建工厂的固定正常状态覆盖数据库值。创建工厂产生尚未持久化的评论，仓储返回数据库自增 ID；已有评论实体必须有正数 ID。实体相等语义围绕稳定身份定义，未保存对象不能简单按 null ID 判为相等；不再依赖 record 的全字段默认相等。

CommentContent 规则继续保留。Comment.ensureLikeable() 检查存在的已持久化身份、一级评论和正常/历史 NULL 状态；NULL 按正常处理保持当前可见规则。前端按钮控制不能替代此检查。

## 仓储与应用能力

| 契约 | 能力 | 实现职责 |
|---|---|---|
| CommentRepository（domain） | 保留 insert；新增 findById | MySQL 读取与恢复评论实体；具体 SQL 和 DO 留基础设施 |
| CommentLikeRepository（domain） | findState；tryApply(change) | Redis 原子验证原状态并切换关系，同时记录待同步标记、递增版本和返回数量 |
| CurrentCommentAuthor（application.port） | 复用 currentUserId | 获取服务端当前用户；后续可按语义调整命名，不因本功能立即全局改名 |
| CommentReadPort（application.port） | 扩展读取 liked | 评论分页读模型继续独立于领域聚合 |
| CommentLikeReadPort（application.port） | 批量读取当前用户状态 | 一页评论一次或少量批量 Redis 查询；状态未知和未点赞区分 |
| CommentLikeCountSyncPort（application.port） | 读取待同步快照、条件写入、条件确认 | 同步 MySQL 投影；任务入口不直接写业务规则或 Mapper |

上述是职责契约，不要求机械地产生每个表格单元对应的 Java 类。错误或竞争必须用明确结果区分，不能把 Redis 超时当作“没有点赞”。Redis 调用结果未知时不得自动重新执行切换。

## 点赞应用流程

在 application.comment.like 建立 ToggleCommentLikeService，与 create/query 并列。

1. 校验评论 ID，从服务端读取当前身份。
2. 检查历史数据是否已核对启用，加载 Comment，执行 ensureLikeable。
3. 读取当前用户的 CommentLike 状态，纯领域方法生成 CommentLikeChange。
4. 由基础设施使用 Redis Lua 比较实际原状态，原子完成关系更新、版本递增及待同步标记记录；同步返回该用户的新状态和当前集合数量。
5. 若原状态已被其他请求改变，确定尚未写入时可以有限次数重新读取和计算；达到上限返回竞争结果，前端读取现状。若请求结果未知，不进行写重试。
6. 返回新状态和 Redis 数量。Redis 原子写确认成功即表示切换成功；不等待 MySQL 计数同步。

Redis 存储键和待同步标记必须能被同一脚本原子操作；若采用 Redis Cluster，应按同步分区安排相同 hash tag，不能使用跨槽全局待同步队列。

当前没有评论状态修改入口。未来增加隐藏/举报更新时，需要单独定义它与点赞资格检查的并发顺序；第一版不宣称跨 MySQL/Redis 具有可串行化共同事务。

## 自动计数同步

在 job 中建立 CommentLikeCountSyncJob，调用 application.comment.like.sync.SyncCommentLikeCountsService。任务入口负责调度，应用服务负责同步流程，基础设施负责 Redis/MySQL 技术细节。

1. Redis 的每次关系变更与待同步标记一同提交，避免进程在关系变更后退出导致永久遗漏同步。
2. 原子读取关系数量、关系版本和恢复代次；使用绝对数量更新 MySQL，不能靠重试累加 +1/-1。
3. MySQL 条件更新：只有新快照版本高于已应用版本才更新 liked 和同步版本，防止旧任务覆盖新结果。
4. MySQL 确认提交后，仅当 Redis 当前版本仍等于已同步版本时移除对应待同步标记；期间出现新点赞则保留标记继续同步。
5. 更新失败、进程退出、确认失败都保留可重试记录；多实例与重复执行依赖版本条件保证安全。

计数同步周期默认 1 秒，正常健康负载下以几秒内可见为目标，故障期间可能更长，不承诺硬实时。每轮限量处理，故障退避并记录告警；恢复后继续消化标记。精确容量配置随实现测试决定。

### Redis 恢复与历史启用

单纯递增 Redis 版本不能覆盖备份恢复：备份可能比 MySQL 旧，待同步标记也可能缺失。因此使用“恢复代次＋代次内版本”，MySQL 持久保存同步代次及版本，Redis 保存当前代次。同步器只接受已启用代次，禁止旧代次任务继续覆盖数据。

恢复备份后暂时禁用点赞写入与同步；先核对关系，再通过受控恢复流程启用更高代次、重建待同步记录，按照已批准数据修复范围更新统计值。完整关系丢失、来源不明确或非零数量无关系的评论继续暂停，不能仅因为 Redis key 不存在就认定数量为零。此处提供恢复设计，不执行任何批量修改，也不承诺恢复备份之后发生但未备份的点赞。

历史启用需要可持久确认的标记，可与同步代次共同表达：未核对的评论处于未启用状态；新评论创建时启用，历史 NULL/0 且无关系在核对后启用。非零且无关系的评论继续显示原 MySQL 数量，按钮不可用，并明确表示待核对。

## 查询与 HTTP 契约

| 接口 | 契约 |
|---|---|
| POST /blog/{blogId}/comments/{commentId}/like | 切换当前用户状态；验证评论实际属于路径博客；返回 liked、isLike |
| GET /blog/{blogId}/comments | 保留原分页和内容字段，新增 liked、isLike、likeAvailable |

liked 的操作结果取 Redis 数量，普通列表取 MySQL 投影，可能暂时不同；前端成功后直接使用操作结果，不立即用滞后的列表覆盖按钮与数量。

登录用户状态不可确认时 isLike 为 null、likeAvailable=false；历史待核对同样禁用。游客 isLike=false，普通可用评论的按钮点击引导登录；不能为了游客显示状态而读取身份关系。NULL 数量且无历史关系按已确认口径显示 0。

未登录写入采用已有 401 行为。目标不合法、不可见、历史未启用通过 CommentRuleViolation 转成既有业务拒绝响应；Redis 写故障采用 HTTP 503，沿用 Result 错误结构，消息为“点赞服务暂时不可用”。状态未知时前端保持数量、显示状态暂不可用，不做乐观切换，不自动重发 POST；恢复时批量刷新状态后启用操作。

第一版无需新增单条状态接口：前端可以重新查询该评论所在分页并按 ID 合并，保持已加载页面；找不到该评论时停止操作并刷新可见列表。不得再次调用切换接口来探测状态。

## 验证重点

| 层次 | 应验证的行为 |
|---|---|
| 领域 | 评论恢复保留真实状态；非法身份、回复、隐藏、被举报拒绝；用户关系切换；不同关系身份不混淆 |
| 应用 | 身份来自服务端；目标匹配路径；历史未启用拒绝；结果未知不重试写入；竞争仅在确定未执行时重新计算 |
| Redis | 比较状态、切换、计数快照、版本和待同步原子性；不同用户并发计数正确；同用户多次请求分别切换 |
| 同步 | MySQL 失败后重试；重复处理不重复加减；旧快照不覆盖新快照；同期新操作不被错误清理标记 |
| 恢复 | 旧代次任务被拒绝；备份回退先核对和重建同步；无关系非零数量不自动归零 |
| HTTP/前端 | 匿名查询、自赞、401、原分页兼容；按钮颜色、防连点、故障禁用、重新读取后恢复 |

Redis 和 MySQL 真实并发与失败行为需要隔离环境验证；纯内存替身和 H2 不能单独证明 Lua、Cluster 或生产 MySQL 事务性质。本设计阶段不连接真实服务。
