# DDD 升级采用九模块渐进迁移并保持兼容

迁移前后端采用 `pojo/common/server` 三个 Maven 模块，业务服务同时承载规则、流程编排和技术实现。2026-10-12 用户确认：DDD 升级先完成一个已有业务试点，再逐步迁移其他业务；目标结构必须采用架构说明中的九个 Maven 模块；现有接口路径、响应格式、数据库表及 Redis 数据含义保持兼容，优先调整内部结构。

九个目标模块为 `domain`、`application`、`infrastructure`、`facade`、`controller`、`job`、`listener`、`service` 和 `start`。采用试点方式，使分层模式能够先在真实业务中验证，再用于其他业务；代价是迁移期间需要管理新旧实现并存。保留九模块是用户明确指定的结构约束，而非 DDD 本身的必要条件。

用户进一步确认首个试点为已有的评论创建与分页查询。先将旧实体、Mapper、Service 和工具安置到 `service`，旧 Controller 安置到 `controller`，启动与装配安置到 `start`，再迁移评论试点。过渡期未迁移接口暂时调用旧 Service，试点接口走新分层。

`facade` 采用进程内门面，依赖 `application`，为 Controller、Job 和 Listener 提供入口并转换对外 DTO，不承载业务规则。这与仅定义接口、由应用层实现门面的方案不同；当前选择保留架构说明中的调用方向。

用户确认九模块与评论试点通过验收后，允许在新分层开发新功能，其余旧业务按需迁移，不必等待全部遗留业务迁移完成。

2026-10-12 已完成九模块安置与评论创建、分页查询的纵向实现：评论 HTTP 入口调用新门面与用例，持久化、身份及作者能力通过适配器复用遗留实现；评论插入和博客计数保持同一事务。领域模型与持久化对象分离，查询使用独立读模型。默认测试使用离线用例与 H2 验证，不将真实 MySQL/Redis 全环境启动当作已验证事实。

遗留层过渡期间承载未迁移业务、旧实体和 Mapper，以及暂未拆出的配置、资源和生命周期。代价是门面为兼容 DTO 仍依赖遗留层，基础设施仍复用旧 Mapper；这些依赖不能进入领域或应用层。每项旧能力完成调用方迁移、契约与事务回归以及资源/生命周期核验后，才具备后续清理条件；任何实际删除仍需依照 AGENTS.md 单独确认，本次不清理。

2026-10-13 用户确认继续迁移评论持久化：在 infrastructure 的 persistence 下建立 CommentDO、CommentMapper 和 CommentRepositoryImpl，评论数据仍写入原 tb_blog_comments，旧 BlogComments、BlogCommentsMapper 和 Service 保留。新仓储独立于旧评论映射；博客计数、作者资料和身份仍复用遗留能力，因此保留 infrastructure → service 的过渡依赖，不引入 service → infrastructure 的循环。身份适配器归入 identity。start 的 MapperConfiguration 同时扫描新旧 Mapper，H2 整链测试共用该配置验证装配与兼容性。

本决策不表示整个系统的业务边界已确认。`content.comment` 仅为本试点实现分包，评论最终所属业务边界及后续迁移顺序仍待讨论。本次不实现任务引擎、保障申诉或 MQ。真实模块依赖、迁移链路和下一业务的迁移方式记录于 [后端架构](../../backend/DDD.md)，运行方法见 [后端说明](../../backend/README.md)。
