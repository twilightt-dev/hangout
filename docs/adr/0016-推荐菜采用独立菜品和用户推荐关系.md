# ADR 0016：推荐菜采用独立菜品和用户推荐关系

- 日期：2026-10-18
- 状态：按已确认方向实施；页面与投稿默认值待用户验收

## 背景

用户已选择按菜品汇总推荐，不要求每个推荐者都重新投稿图片。同店同名不重复创建，不同用户的推荐合并为人数，列表按人数、时间和 ID 降序。当前先补齐独立业务，暂缓商详任务链。

## 决策

1. tb_recommend_dish 保存菜品，tb_recommend_dish_user 保存推荐事实，以 (dish_id,user_id) 联合主键保证同用户不重复计数。
2. 主表维护 recommend_count，以同事务插入推荐关系并原子加一；推荐操作采用 PUT 表示明确设置为已推荐，重复调用保持相同状态。
3. 同店菜名去除首尾空白后，以 UTF-8 字节组成 name_key 并建立 (shop_id,name_key) 唯一键，避免 MySQL 默认排序规则把不同名称意外视为相同。
4. 新增按店铺行加锁，推荐按菜品行加锁；写事务采用 READ_COMMITTED，锁等待后读取最新提交。读事务采用 REPEATABLE_READ，保证一次分页的总数、列表及推荐状态来自同一快照。
5. (user_id,request_id) 唯一键支持创建重试；竞争失败必须先回滚，再在新事务中读取已有提交，不在失败事务内继续查询。
6. domain 不依赖框架，application 不依赖旧 service，业务按现有 DDD 模块独立实现；前端复用现有上传能力，领域模型只接收图片路径。

## 取舍

冗余人数换取按热度查询的简单性，但所有业务写入必须同时维护明细和计数。行锁将同一菜品的推荐写入串行化，当前规模接受这一取舍。单店投稿也串行，以明确处理同名并发；数据库唯一约束是最终防线。

推荐人数随时间变化，页码分页不承诺跨请求排名快照。上传文件的所有权校验、取消推荐和内容审核不在本轮最小实现内；这些不是已批准的长期限制。

## 验证

使用真实 Mapper、事务、HTTP 与隔离 H2 执行建表 SQL，验证推荐去重、并发人数一致、同名和重试冲突、分页排序及回滚。真实 MySQL 的隔离行为和完整图片上传链路须另行联调。
