# 共享任务链采用固定阶段与节点结果隔离

为后续复杂用例引入共享任务链，用户在 2026-10-16 的三轮设计访谈中确认以下九项选择，并随后明确调用 implement 开始开发。本 ADR 记录核心语义，接口和工程默认约定见设计清单。第一版现已实现，通过公开行为测试、默认后端完整回归及独立规范/规格审查；具体业务接入另行验证。

| 决策 | 已确认内容 | 选择依据 |
| --- | --- | --- |
| 阶段模型 | 沿用 PRE_VALIDATION、PRE_PROCESSING、DATA_PROCESSING、DATA_INSERTION、POST_PROCESSING；各链通过 PhaseConfig 选择需要的阶段及顺序 | 保持与已学习模型一致，先支持明确的阶段式编排，不要求业务自行定义阶段 |
| 节点重要性 | 区分必需节点与可选节点；必需失败阻断后续阶段，可选失败允许继续并保留诊断 | 必要数据缺失和允许缺少的辅助数据不能采用同一种处理方式 |
| 并行数据 | 各节点读取约定输入并产出独立结果，阶段收尾时统一合并；同阶段节点不消费彼此未完成的输出 | 避免所有节点实时修改同一属性容器，使成功、失败及迟到结果可以被明确取舍 |
| 同名结果冲突 | 同一并行阶段多个节点产出同名 key，直接报错，拒绝本阶段合并并终止链路 | 将节点之间的数据约定冲突显式暴露，不以完成时间或 order 覆盖结果 |
| 必需节点失败 | 引擎观察到必需失败后尽快结束等待并返回失败，不再等待当前阶段所有节点完成；保留首先观察到的导致终止的错误 | 后续处理条件已不成立，避免失败响应继续受其他慢节点牵制；可选失败单独记录 |
| 超时层级 | 第一版只支持阶段级超时，串行与并行阶段都生效；串行节点共同消耗同一阶段预算 | 先提供完整的阶段等待边界，避免尚未明确语义的多层超时相互覆盖 |
| 可选节点超时 | 阶段到期时若必需节点均已成功，仅剩可选节点未完成，则将未完成节点记为超时，只合并成功结果并继续；仍有必需节点未完成则链路失败 | 异常与超时沿用一致的必需/可选语义 |
| 输入只读 | 节点读取的输入和前序结果遵守只读约定，修改通过新对象提交；不由引擎通用深拷贝 | 结果容器独立并不能自动隔离内部可变对象，节点需要遵守明确的数据访问约定 |
| 失败出口 | 引擎返回 TaskContext，执行故障通过失败结果及原因表达，可选失败单独记录；注册或参数使用错误抛出明确异常 | 应用调用方统一检查执行状态，不把可选失败混成整条链路失败，也不把 output 非空当作成功 |

考虑过继续使用教学项目的共享 ConcurrentHashMap 属性容器，但这会把同名写入、可变对象修改和结果接受时机交给各节点自行协调。采用独立结果后，结果合并成为引擎的明确职责，节点不能依靠同阶段另一个节点恰好已经写入的数据。

提前结束后，该阶段的迟到结果不再进入已返回的链路状态；可以尽力取消剩余任务，但不承诺已运行任务立即停止，也不承诺撤销节点已经产生的外部副作用。快速失败要求执行器能够在等待全部节点完成之前响应必需失败；仅在最终合并时保留首个错误，不等于快速失败。

## 后续落实

输入只读是节点协议，不意味着引擎能自动禁止任意业务对象的 setter。引擎自己的属性映射、写集和诊断集合提供只读容器接口，业务使用不可变对象或显式复制共同落实该协议。输入、输出及属性值保留实际类型，不将未知泛型集合自动替换为另一种包装类型，以免破坏调用方的类型约定。

节点诊断类型、失败节点写入取舍、output 合并、注册校验、线程池配置及验收清单见[任务链第一版设计](../design/taskchain-v1.md)。用户已明确要求开始实现，本轮采用清单中的工程默认值；实际业务接入与生产容量另行验证。模块范围及既有业务约束见根目录 CONTEXT.md 的“共享任务链”章节。
