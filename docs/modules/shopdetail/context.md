## 模块目标

围绕一家店铺聚合首次展示所需的数据，帮助用户判断是否到店；通过可编排任务链组织并行查询、结果组装和衍生信息生成，支持辅助区域独立失败。

## 负责范围

- 基本信息区、优惠与套餐区、店内推荐区、评价信息区、达人探店区、周边推荐区的首次展示聚合。
- 调用各业务的查询能力，汇总评价统计，生成基于评价与探店博客的推荐标签。
- 依据当前店铺的位置和类型推荐周边店铺。
- 区分查询成功、成功但无数据、查询失败和超时。
- 2026-10-19 已交付后端首次展示聚合、前端六区接入和缺少的必要查看更多接口。
- 商详缓存与预热的负责范围及实施状态见[商详缓存策略](cache.md)。

## 不负责范围

- 不在商详读取过程中发布评价、投稿菜品、推荐菜品或修改业务数据。
- 查看更多、评价分页、发布评价等操作使用独立接口，不重复执行整条首屏任务链。
- 不合并店铺评价与探店笔记，不新增达人认证体系。
- 不在读取商详或缓存预热时增加店铺访问统计；成功展示后的访问上报沿用独立业务。
- 缓存的写后一致性边界见[商详缓存策略](cache.md)。

## 核心概念

| 概念 | 含义 |
|---|---|
| 首次展示聚合 | 一次任务链执行取得页面首次展示所需的多个业务结果 |
| 基本信息区 | 店铺自身基础资料，以及评价统计、推荐标签等其他结果的展示汇总；原称首屏摘要区 |
| 基本事实 | 基础资料、优惠券、套餐、推荐菜、评价、探店笔记等查询取得的数据 |
| 衍生结果 | 依据已有事实计算或筛选得到的信息，例如推荐标签；不以“能否只用 shopId 查询”划分职责 |
| 达人探店 | 展示所有用户关联当前店铺的可展示探店笔记的栏目，不要求作者有达人认证 |
| 周边推荐 | 以当前店铺为中心的同类型店铺推荐，与以用户定位为中心的附近店铺列表不同 |
| 局部不可用 | 辅助查询失败或超时，其他成功区域仍可展示；不能用空列表或零值伪装成功 |

## 主要业务流程

2026-10-19 已实现的实时查询采用下列编排。缓存优先与实时补齐流程见[商详缓存策略](cache.md)；下表描述回源时的聚合能力：

| 步骤 | 职责 |
|---|---|
| 入口校验 | 校验店铺 ID 等请求参数，简单参数校验不必单独占用阶段 |
| DATA_PROCESSING，并行，默认 2 秒 | 查询店铺基础资料、优惠券、套餐、推荐菜、评价及统计、探店笔记；基础查询必需，其余可选 |
| POST_PROCESSING，串行，共享默认 1 秒 | 必需的 AssembleShopDetailNode 先生成可返回的组装结果；随后可选的 EnrichShopDetailNode 调用领域服务生成标签及周边推荐 |
| 返回 | 必需任务失败返回整体失败；辅助区域失败保留其他成功结果 |

无需为了使用全部枚举而填充五个阶段；当前商详读取用例没有 DATA_INSERTION 的写入需求。

## 数据模型

| 模型 | 职责与现状 |
|---|---|
| ShopDetailAggregate | 普通业务数据组合，直接保存各仓储查询结果、推荐关系与衍生数据，不包装任务执行状态 |
| ShopDetailTaskContext | 继承 TaskContext<Long, ShopDetailAggregate>，承载输入、节点数据与输出 |
| ShopVoucher、ShopSetmeal、RecommendDish | 优惠券、套餐和推荐菜；已有独立业务规则继续生效 |
| ShopReview、ShopReviewSummary | 评价明细与统计摘要，数量和均分基于全部评价，近期标签采用下文约定样本与规则 |
| ShopVisitBlog | 关联当前店铺的探店笔记及展示资料 |
| ShopRelatedShop | 周边推荐店铺及其相对当前店铺的距离 |
| ShopDetailDomainService | 统一组合仓储读取、同步聚合与 enrichShopDetail 增强，封装标签、周边推荐等跨对象规则；不负责引擎编排或 HTTP 返回包装 |

页面分区不直接决定实体或聚合边界。基本信息区不因是独立展示区域而必然新增领域实体。

domain 定义业务模型、仓储接口和领域规则；application 负责节点与用例编排，在 model.result 定义响应模型；infrastructure 实现查询；Facade 转调应用服务；Controller 处理 HTTP 和可信身份。沿用项目 Result 外壳，业务结果类型不直接依赖旧 service 模块模型。

### 应用层业务分包

用户确认 application 以 `com.dianping.shop` 为总包，先按业务归类，再按请求、响应和用例职责分包：

| 包 | 负责范围 |
|---|---|
| `recommend.model.request`、`recommend.model.result`、`recommend.service` | 推荐菜投稿、用户推荐及独立分页 |
| `review.model.request`、`review.model.result`、`review.service` | 店铺评价发布、独立分页及预设标签 |
| `setmeal.model.result`、`setmeal.service` | 套餐响应与独立查询；分页条件使用共享请求，没有专用请求时不创建空包 |
| `shopdetail.model.result`、`shopdetail.service` | 首屏聚合响应、分项执行状态、任务链入口与商详其他查看更多查询 |
| `shopdetail.task` | 商详业务上下文、查询节点、组装和增强节点；当前仅该业务使用任务编排 |
| `shared.request.ShopListPageRequest` | 店铺列表共享分页条件，校验店铺标识、页码、每页数量与偏移量溢出 |
| `shared.result.ShopPageResult<T>` | 店铺各业务共享的应用层分页响应，承载记录、总数、页码、每页数量和总页数 |

`ShopDetailResult` 保留在 `com.dianping.shop.shopdetail.model.result`，表达整页首次展示的聚合响应；`SectionResult` 也保留在该包维护商详分项状态。原 `ShopDetailPageRequest` 更名并迁移为共享的 `ShopListPageRequest`；首屏入口只校验店铺标识，不构造分页请求。已有推荐菜和评价的专用分页响应继续保留，避免此次分包重构改变接口契约。

本次仅调整 application 的业务分包，domain、infrastructure、Facade 和 Controller 的类归属保持原有设计，并同步引用新应用层类型。`shared` 属于 application 内店铺业务共享模型，不代表新增共享领域。HTTP 路径、JSON 字段与任务链节点元数据不因分包改变。

2026-10-19 用户明确要求按教学项目简化商详应用服务，职责进一步统一为：

| 入口或组件 | 负责范围 |
|---|---|
| ShopDetailDomainService.getShopDetail | 按教学项目形式直接调用仓储并逐项赋值，最后调用 enrichShopDetail；查询异常向上抛出，不强求同步路径也逐区降级 |
| ShopDetailDomainService.enrichShopDetail | 直接读取近期语料、生成口碑和评价标签、查询周边店铺并补齐组合对象；不包装任务执行状态 |
| ShopDetailApplicationService.getShopDetail | 校验请求，选择同步领域聚合或任务链，检查执行成功与否并转换响应；不承担优惠、标签、周边等业务推导 |
| 查询节点、Assemble、Enrich | 查询节点复用领域读取能力；Assemble 汇集业务数据；Enrich 调用领域能力并分别记录来源故障。上下文在引擎结束后补齐未提交分项的失败或超时状态 |
| ShopDetailResult.from | 将普通领域数据与应用执行状态合成响应，不查询仓储、不生成业务衍生结果；同步成功结果按实际数据判断空结果 |
| ShopDetailQueryService | 只承接优惠券、博客与周边的独立查看更多用例，不参与首屏任务链，不再集中持有所有仓储 |
| 仓储实现 | 多语句分页、套餐明细和评价统计在调用线程内开启独立只读、可重复读事务，保证单次读取内部一致；原有写用例事务不变 |

只有未装配 TaskChainEngine 时采用同步路径；已经开始执行的链路失败按既有 404、503、504 等契约返回，不串行重试整条链路。同步路径不承诺引擎阶段预算，生产仍使用已装配的任务链。

2026-10-19 用户进一步明确采用教学项目的直接查询形式，取消领域分项包装。此前领域 ShopDetailSection 的方案被本决定替代：领域组合只保存业务数据；任务链的成功、失败、超时和部分来源可用等状态由 application 的上下文与现有 SectionResult 维护。同步查询任一仓储故障将向上抛出，由应用入口统一转换异常。任务链路径继续保留局部降级；两条路径仅要求成功时业务结果与规则一致。

domain 保留已有 Lombok provided 依赖；开发时调整架构测试，仅允许此编译期依赖例外，仍禁止领域层依赖 Spring、数据库框架和旧 service 模块。ArchitectureLayoutTest 已按这一边界调整，Lombok 仅作为编译期例外。

商详上下文的业务 getter/setter 应通过父类 getAttribute/setAttribute 访问节点数据，参与快照、写集和阶段合并；不得用普通字段绕过并行隔离。已发布到上下文的可变对象不能通过原地修改绕过写集。

## 对外接口

| 用例 | 契约状态 |
|---|---|
| 首次展示聚合 | 新增 GET /shop/{shopId}/detail，返回业务组合结果与区域状态 |
| 评价发布与分页 | 沿用已有独立接口，详见店铺模块文档 |
| 套餐查询 | GET /shop/{shopId}/setmeals 同步改为分页并更新调用方；商详首屏最多 4 个上架套餐，每项包含明细与使用规则 |
| 推荐菜投稿、推荐与分页 | 沿用已有独立接口，详见店铺模块文档 |
| 探店笔记按店铺查看更多 | 首屏少量展示，后续通过独立接口分页，默认每页 10 条 |
| 周边推荐查看更多 | 首屏少量展示，后续通过独立接口分页，默认每页 10 条，沿用当前店铺中心、同类型与 5 公里范围 |

新增分页默认每页 10 条，已有评价与推荐菜接口保留现有参数约定。各区域响应区分成功、成功但无数据、失败、超时；具体堆栈仅记录在服务端。

新增分页每页允许 1～50 条。前端点击查看更多进入对应列表，从第 1 页查询，后续点击“加载更多”；不把首屏预览直接拼接到独立分页结果，避免重复展示。跨请求排序数据变化时，不承诺固定数据快照。

游客可浏览六区；登录后返回当前用户是否已推荐菜品、是否已点赞博客。Controller 从可信认证信息取得用户身份，显式传入商详上下文，异步工作线程不自行读取请求线程的登录 ThreadLocal。

当前实时查询链路中，列表局部失败时通过对应独立接口重试；标签增强失败先通过刷新详情恢复，不新增标签专用重试接口。推荐、点赞和发布成功后刷新相关数据；启用缓存后的刷新与时效边界见[商详缓存策略](cache.md)。

## 业务约束

- 店铺基础资料、参数校验和结果组装是必需职责；必需任务失败结束链路。
- 优惠券、套餐、推荐菜、评价、探店等辅助查询允许局部失败；优惠券与套餐分别返回查询状态。
- 基本信息区评分与评价数量使用新评价统计，不读取可能滞后的旧详情缓存统计；评价不可用时只使相关统计不可用。
- 推荐标签来源于当前店铺的评价和探店博客，不把图片示例中的认证、收录年限或服务承诺当作已证实事实。
- 周边推荐以当前店铺为中心，限定同类型、半径 5 公里，排除当前店铺；按距离升序、店铺 ID 升序排列，距离文案使用“距该店”。
- 探店笔记按点赞数降序、发布时间降序、笔记 ID 降序排列，不计入店铺评分与评价数。
- 阶段预算可配置，默认并行查询 2 秒、串行后处理 1 秒。基础查询或组装失败、超时则整体失败；仅可选节点失败或超时则局部降级，预算后续按实测调整。
- Assemble 为必需节点，先产出可返回结果；Enrich 为可选节点，内部独立处理标签与周边故障。整个 Enrich 失败或超时时保留组装结果，并将未完成的增强内容标为不可用；不修改已提交的组合对象来绕过节点结果丢弃。
- 店铺坐标缺失或无效时，周边区域说明“缺少位置信息，暂无法推荐周边店铺”，其他区域正常展示；该状态与成功查询但附近无同类店铺不同。

### 优惠券

- 展示上架普通券和未过期秒杀券；未开始或已售罄的秒杀券保留，并标明对应状态。
- 当前可购买的优惠券优先，其后按支付金额升序、优惠券 ID 升序排序；首屏和独立分页沿用相同规则。
- 购买继续走现有交易接口，不在商详聚合中新增交易逻辑。
- 优惠券与套餐的缓存边界见[商详缓存策略](cache.md)。

### 近期口碑标签

- 基本信息区标签统计近 90 天的最新 200 条评价和最新 50 篇关联博客；独立取得统计语料，不以首屏预览列表作为统计全集。
- 评价使用用户选择的预设标签；博客按同一固定词典匹配，只采纳明确正向表述。否定或含义不明确的句子不贡献标签。
- 两类来源合并后，同一用户对同一标签最多贡献一次；至少 2 名用户提及才入选，按提及人数降序、固定词典顺序打破并列，最多展示 5 个。
- 页面称为“近期口碑标签”；不从文本推断官方认证、收录年限或停车等确定的服务承诺。
- 一个来源查询失败时，使用成功来源并标记统计不完整；两个来源都失败时，标签暂不可用。成功但无标签须与故障区分。
- 评价信息区的高频标签只统计评价来源；基本信息区的口碑标签合并评价与博客来源。
- 第一版固定词典沿用现有八个评价标签，博客匹配到同一词典：味道好、环境好、服务热情、价格实惠、干净卫生、交通方便、出餐快、停车方便。停车方便仅作为用户口碑，不表示停车设施或免费停车承诺。
- 评价区同样使用近期评价样本、按用户去重、至少 2 名用户入选、最多 5 个标签，排序沿用提及人数降序与词典顺序。
- 标签统计语料查询、首屏列表和评价统计分开处理失败。语料查询失败只影响相应标签来源；列表、评价统计等成功部分继续展示，不因标签提取故障隐藏成功的评价或博客。

## 已实现的接口与分层

| 模块 | 入口与职责 |
|---|---|
| domain | ShopBaseInfo 保存店铺自身资料；ShopDetailAggregate 直接组合业务数据；领域服务统一同步联合查询、标签及周边业务规则 |
| application | ShopDetailApplicationService 选择领域同步入口或编排任务链；ShopDetailQueryService 承接独立分页与响应转换；task 下六个查询、Assemble、Enrich，不维护跨对象业务推导规则 |
| infrastructure | JDBC/MyBatis 直接读取业务表；博客个人点赞状态读取现有 Redis 集合；不调用旧 Service |
| facade / controller | 转调应用用例；Controller 取得可信 UserDTO 身份并显式传入，沿用 Result 响应外壳 |
| frontend | ShopDetailView 接收一次聚合结果；ShopSectionListView 从第 1 页独立查询；写操作走已有接口并刷新对应列表 |

| HTTP 接口 | data 结构 |
|---|---|
| GET /shop/{shopId}/detail | shop、vouchers、setmeals、recommendations、reviews、statistics、blogs、decisionTags、reviewTags、relatedShops、recommendationStateAvailable |
| GET /shop/{shopId}/vouchers?current=1&size=10 | records、total、current、size、pages |
| GET /shop/{shopId}/blogs?current=1&size=10 | 同上；带当前作者资料，isLike 为个人状态，故障时为 null |
| GET /shop/{shopId}/related-shops?current=1&size=10 | 区域状态包装分页，缺坐标或类型时 UNAVAILABLE |
| GET /shop/{shopId}/setmeals?current=1&size=10 | records、total、current、size、pages；替代原套餐数组，前端已同步 |

区域统一使用 status、data、message。SUCCESS / EMPTY / PARTIAL 是可用结果，FAILED / TIMED_OUT / UNAVAILABLE 没有伪造数据。整体非法参数返回 400、店铺不存在 404、必需任务超时 504、其他必需依赖故障 503；单个可选任务故障保持 HTTP 200，并在对应区域表达状态。优惠券 availability 为 AVAILABLE、UPCOMING 或 SOLD_OUT。

语料读取由可选 Enrich 调用领域能力完成，避免语料阻塞导致已查询的评价和博客列表被整个查询节点丢弃。每个节点按写集整体提交；Enrich 整体超时时，其标签和周边增量均丢弃，保留 Assemble 的输出。分项异常使用 application 的 SectionResult 及上下文表达，领域模型不保存执行状态。领域组合允许 setter 赋值，但任务节点必须先复制组合对象再修改，不能原地修改已经发布的输出。

每个公开分页读取在自己的只读可重复读事务内取得计数和列表；各查询节点之间不共享数据库事务，也不承诺整页或跨分页请求的同一数据库快照。上下文隔离不会深复制业务对象，节点遵守已发布值只读、通过新对象替换的协议。

当前配置入口为 shop-detail.query-timeout-ms（默认 2000）及 shop-detail.post-timeout-ms（默认 1000）。本轮不新增业务表，仍依赖既有评价、套餐、推荐菜迁移完成。主要架构取舍见 [ADR 0017](../../adr/0017-商详采用首次展示任务链与独立分页.md)。
