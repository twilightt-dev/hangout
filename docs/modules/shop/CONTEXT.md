## 店铺评价

### 模块目标

2026-10-16 用户确认先补齐独立的店铺评价业务，暂不开展商详任务链接入。发布、分页、统计同步和商详展示代码已完成，数据库迁移脚本仍需按部署环境审阅执行；开发规格见[店铺评价第一版设计](shopreview-design.md)。

### 负责范围

发布评价、按店铺分页查看评价、商详页面展示评价列表，以及更新店铺总体评分和评价数量。

### 不负责范围

本轮不开展商详任务链编排。作者修改与删除不在已选择的第一版范围内；回复、点赞、审核、图片评价等扩展尚未纳入范围。

### 核心概念

**店铺评价**：用户针对一家店铺发布的独立评价，与博客评论不同；同一用户可以对同一家店铺发布多条评价。

**总体评分**：用户独立填写的总体感受，不由分项评分计算。

**分项评分**：分别表达口味、环境、服务体验的评分。

**店铺总体评分**：仅以本次新增评价功能保存的总体评分计算平均分，每条评价分别计入，同一用户发布的多条评价不按用户去重；旧店铺汇总评分不作为计算基数。

**评价数量**：仅统计本次新增评价功能保存的评价记录，不按评价作者去重，不混入旧店铺汇总数量。

**预设评价标签**：由系统提供、用户选择的评价描述；第一版包含“味道好”“环境好”“服务热情”“价格实惠”“干净卫生”“交通方便”“出餐快”“停车方便”。不接受用户任意创建标签，后端统一提供选项并校验提交值。

**一次评价提交**：前端为一次主动发布生成 UUID；该次发布及其网络重试使用同一个提交标识，只保存一条评价。同一用户与提交标识构成唯一身份，同内容重试返回原评价 ID，同标识不同内容返回冲突错误；主动再次发布使用新标识，可以生成另一条评价。

### 主要业务流程

登录用户对存在的店铺发布评价，不要求订单或优惠券核销凭证；发布时校验评分、正文及预设标签，重复提交标识不重复新增评价。application 使用同一数据库事务保存评价及更新统计，通过店铺行锁协调同店并发发布，失败全部回滚，不引入 Redis 锁。分页用例公开可读，查询一页评价后批量补齐作者当前昵称与头像，资料缺失时保留评价并使用默认展示。

### 数据模型

按用户确认简化模型：不单独定义 ReviewAuthor、ReviewStatistics。ShopReview 直接包含 userName、userIcon，分页通过左关联查询补齐当前资料；这两个展示字段不持久化到评价表。评价数量与总体评分总和由仓储返回标量，应用服务统一计算并写入店铺统计，不把店铺级统计字段混入单条评价。基础设施 DO 使用 Lombok @Data 生成访问方法。

评价围绕店铺 ID、作者 ID、总体评分、口味评分、环境评分、服务评分、正文、预设标签、提交标识和发布时间建模。四项评分全部必填，均为 1～5 分，支持 0.5 分步长；内部按分数乘 10 的整数表示，店铺平均分展示一位小数。正文必填，去除首尾空白后长度为 1～1000 个 Java UTF-16 单元，按纯文本展示，不支持 HTML。标签非必填、最多选择 5 个，去重且不接受空白或非预设值。作者昵称与头像采用查询时的当前用户资料。

### 对外接口

发布使用 POST /shop/{shopId}/reviews，要求登录；分页使用 GET /shop/{shopId}/reviews?current=1，标签选项使用 GET /shop/review-tags，均允许游客访问。每页固定 10 条，按 createTime 与 id 降序；无评价或超过末页返回空列表，非法页码报错。分页结果同时包含店铺评价数量及平均分，统计直接查询数据库，不从旧商详缓存中读取。application 中使用 model.request 定义应用服务输入，使用 model.result 定义业务返回数据；Controller 复用既有 Result<T> 包装 HTTP 响应，业务返回类型不等同于该响应外壳。

无评价时返回数量 0、平均分 null，页面显示“暂无评分”；tb_shop.score 使用 0 表示无评分。有评价时平均分四舍五入保留一位小数。参数错误为 HTTP 400、未登录为 401、店铺不存在为 404、同提交标识不同内容为 409，错误响应沿用 {code,msg,data}。

### 业务约束

允许同一用户对同一店铺发布多条评价，不以 (shop_id, user_id) 唯一约束限制发布；同一次提交的网络重试只生成一条评价。总体与分项评分独立表达，店铺平均分不使用分项评分计算。作者身份来自服务端认证信息。

### 已确认的设计

- 新评价业务在 domain、application、infrastructure、facade、controller 中实现，不通过适配器调用旧 service 的业务实现。
- infrastructure 中的新仓储直接完成所需持久化访问；旧博客评论保持当前实现。
- application 保持现有内层依赖约束，不为使用旧 Result<T> 增加对 service 的依赖。
- 应用层包含 ShopReviewApplicationService；输入统一组织在 model.request，输出组织在 model.result，不再按 command/query 分包。
- 2026-10-16 用户确认第一轮规则：四项评分必填、正文必填且不超过 1000 个 UTF-16 单元、系统预设标签、作者当前资料、登录即可评价、固定 10 条按时间及 ID 倒序分页，以及同次提交幂等。
- 用户确认第二轮第 8～12 项：八个预设标签、仅按新评价计算统计、同事务及店铺行锁、分页结果直接提供最新统计，以及用户与 UUID 提交标识的幂等语义。
- 商详页面顶部评分与评价数量使用新评价分页结果提供的统计；基础店铺信息继续使用既有缓存。tb_shop 同步维护新统计，供既有列表排序读取；旧 GET /shop/{id} 中缓存的统计字段仍可能滞后，不作为新页面统计来源。
- 用户确认第三轮第 13～17 项：普通店铺新增的统计统一为 0，普通修改忽略请求中的 score/comments；无评价及平均分舍入规则、三个 HTTP 路径、发布后的刷新与重试、错误状态和缺失作者资料的展示均已确认。
- 作者资料缺失时昵称显示“用户资料暂缺”，头像采用前端默认头像展示，评价不丢弃。
- 发布成功后清空表单并重新查询第一页及统计。刷新失败提示“评价已发布，列表刷新失败”，不重新发布；网络结果不明时保留内容和提交标识，重试复用标识。
- 用户已经建立的模型、仓储、门面与持久化骨架需保留；第一版业务代码已实现，真实数据库迁移尚未执行。Git 提交仅在用户明确要求时进行。

## 店铺套餐

2026-10-18 完成第一版业务设计与实现。本文记录套餐业务语言、展示规则、数据模型及接入边界；建表与演示 SQL 已提供，尚未执行到实际业务数据库。

### 模块目标

补齐店铺套餐展示业务，让用户在店铺详情中了解套餐及其固定内容、价格和使用规则。

### 负责范围

店铺详情中的套餐列表、套餐详情，以及套餐基本信息、固定菜品明细和使用规则展示。

### 不负责范围

优惠券属于独立业务，不将优惠券作为套餐，也不将套餐并入优惠券业务。

本期不包含套餐购买、下单、模拟或真实支付、到店核销、退款等交易与履约流程，不增加套餐新增、编辑、上下架管理页面或写接口，不展示库存、销量或购买按钮。

本期不接入商详聚合与共享任务链，留待后续与用户一起开发。套餐通过独立查询接口接入现有商详页面展示；页面增加套餐区块不等于后端商详聚合或任务链接入。

### 核心概念

**店铺套餐**：店铺提供的固定内容组合，例如“99 元双人餐”，明确列出包含的菜品、数量和使用规则。

**套餐内容**：套餐中固定包含的菜品明细，每项以名称、数量和单位表达，例如“烤鱼 × 1 份”。第一版不包含“主菜二选一”等可选组合。

**套餐基本信息**：用于介绍套餐的名称、封面图、套餐价和适用人数；原价和简介为选填信息。

**套餐价**：套餐对外展示的组合价格。本期只展示该价格，不据此发起支付。

**上架套餐**：允许在店铺套餐展示中被访问的套餐。下架套餐不向展示查询返回，本期不提供修改状态的入口。

**展示顺序**：套餐列表使用的预设排列顺序，排序值越小越靠前，相同时按套餐 ID 升序排列。

**使用规则**：说明套餐如何使用及其限制的多行纯文本。本期不将有效期、可用时段和预约要求等拆成独立规则字段。

**优惠券**：与套餐分别建模、分别存储的独立业务概念，不作为套餐的别称；其详细定义由优惠券业务维护。

### 主要业务流程

登录用户或游客浏览店铺详情中的上架套餐列表，列表按排序值、套餐 ID 依次升序排列；查询列表时一并返回菜品和使用规则，点击套餐卡片后直接在商详内展开，不另开详情页面，也不再次请求详情。本期流程止于信息浏览，不进入交易与履约。

店铺没有可展示套餐时隐藏整个套餐区块；套餐加载失败时在区块内提示并提供重试，不阻断店铺其他详情内容。

图片加载失败时显示占位图；未提供原价或简介时隐藏对应信息，不用虚构数值或文字补齐。必需数据不合法时返回错误，套餐区显示失败状态，不展示残缺套餐或伪装为空列表。

### 数据模型

用户已确认本轮为套餐独立建表，不复用优惠券表，不建立共享菜品库。

| 表 | 负责内容 | 关联 |
|---|---|---|
| `tb_shop_setmeal` | 店铺套餐主信息、使用规则、上下架状态与展示顺序 | 归属于店铺 |
| `tb_shop_setmeal_item` | 套餐内固定菜品的名称、数量和单位 | 归属于一个套餐 |

套餐菜品是套餐内的独立条目，不作为跨套餐共享的菜品实体。领域模型 `ShopSetmeal` 包含明细集合，明细不单独设置仓储。

已确认的业务信息包括：

| 信息 | 已确认要求 |
|---|---|
| 基本信息 | 名称、封面图、套餐价、适用人数 |
| 可选信息 | 原价、简介 |
| 菜品明细 | 固定菜品组合，每项包含名称、数量、单位 |
| 使用规则 | 支持换行的纯文本 |

金额以整数分保存，展示时换算为元；套餐价大于 0，原价可空且不低于套餐价。适用人数为正整数，菜品数量为正数且最多保留两位小数。每个套餐至少包含一项菜品，套餐名称和使用规则不能为空。

已提供独立的演示数据 SQL，覆盖上架、下架及多菜品套餐，供后续联调使用。演示数据不等同于真实经营数据；本轮未执行实际业务数据库建表或数据写入。

持久化约定：主表 `status=1` 为上架、`0` 为下架，默认下架；主表以 `(shop_id,status,sort,id)` 建立查询索引，明细以 `(setmeal_id,sort,id)` 建立索引并关联套餐主键。主表与明细在同一只读可重复读事务中查询，明细批量读取，按排序值和明细 ID 升序返回。字段名与长度以[建表脚本](../../../backend/infrastructure/src/main/resources/db/migrations/20261018_shop_setmeal.sql)为准。

### 对外接口

2026-10-19 套餐接口已随商详改造：`GET /shop/{shopId}/setmeals?current=1&size=10` 返回分页对象 records、total、current、size、pages，默认每页 10 条，上限 50。首屏聚合最多 4 个，每个套餐仍带明细和规则。公开可读，按 sort、id 升序；前端查看更多进入独立列表，展开卡片不再请求详情。

响应沿用 `{code,msg,data}`，`data` 为分页对象，套餐位于 records。每个套餐提供标识、名称、封面图、套餐价、可选原价、适用人数、可选简介、固定菜品明细及使用规则；明细提供名称、数量和单位。金额字段使用整数分，不与展示的元混用。

| 场景 | HTTP 状态与结果 |
|---|---|
| 店铺存在且有上架套餐 | 200，返回包含本页套餐的分页对象 |
| 店铺存在但没有上架套餐 | 200，`data.records` 为 `[]`，total 为 0 |
| 店铺 ID 非法 | 400 |
| 店铺不存在 | 404 |
| 数据库不可用 | 503 |
| 套餐必需数据不合法 | 服务端错误，前端显示套餐区加载失败，不返回残缺套餐 |

展开详情不另发查询，不提供独立详情查询或套餐管理写接口。

Java/JSON 字段使用 `id`、`shopId`、`name`、`coverImage`、`price`、`originalPrice`、`people`、`description`、`rules`、`items`；明细字段为 `name`、`quantity`、`unit`。成功响应 `code=1`，错误响应 `code=0`，不合法必需数据返回 HTTP 500。

### 业务约束

套餐与优惠券是两个不同的业务，分别使用不同的表存储。本期仅提供展示，不提供套餐购买及履约能力。

菜品全部固定，不支持用户选择或替换组合；每个套餐至少包含一项菜品。套餐名称和使用规则不能为空。原价、简介允许不提供。使用规则按支持换行的纯文本表达，不包含 HTML 或富文本。

### 负责范围

新增菜品、上传单张封面、推荐关系去重、人数统计、公开分页、登录用户推荐状态，以及现有详情页中的独立推荐菜组件。

### 核心概念

**推荐菜**：某家店被用户收录的一道菜，多用户推荐汇总为一张卡片。

**推荐关系**：一个用户对一道菜的一次有效推荐，以菜品与用户联合唯一约束去重。

**推荐人数**：推荐关系中的不同用户数，不是按钮点击次数。

**投稿提交标识**：用户发起一次创建操作时生成的 UUID；同一用户对同一标识的相同内容重试返回原菜品，不能重复创建。

### 主要业务流程

新增：服务端取得当前用户 → 校验菜名与图片路径 → 事务内锁定店铺 → 检查提交重试与同店同名 → 插入菜品及创建者推荐关系 → 增加人数 → 返回菜品卡片。

推荐：事务内锁定当前店铺的目标菜品 → 已推荐则直接返回 → 未推荐则插入关系并增加人数。任一步失败都回滚。写事务采用已提交读与行锁配合，不依赖 JVM 内存锁。

查询：在同一个只读可重复读事务中确认店铺存在、统计菜品数量、按既定顺序分页并批量读取当前用户的推荐状态。游客也能读取列表。

2026-10-19 商详首次通过聚合接口取得 6 道，查看更多进入独立列表，从第 1 页加载。发布结果不明时保留表单与提交标识；成功后刷新失败只重试读取，不重复发布。切换店铺或身份后忽略旧请求结果。

### 数据模型

| 表 | 内容与约束 |
|---|---|
| tb_recommend_dish | 店铺、创建者、提交标识、菜名、封面、推荐人数及创建时间；同店规范化菜名唯一，创建者与提交标识唯一 |
| tb_recommend_dish_user | 菜品、推荐用户、推荐时间；菜品与用户联合主键，外键关联菜品 |

菜名去除首尾空白后，使用其 UTF-8 字节作为 name_key，避免数据库默认不区分大小写或重音的排序规则扩大“同名”范围。人数与明细在同一事务更新。

架构取舍见 [ADR 0016](../../adr/0016-推荐菜采用独立菜品和用户推荐关系.md)，实施与检查记录见[推荐菜实施记录](recommend-dish-implementation.md)。

## 商详周边推荐（设计中，待实现）

### 已确认的设计

- 用户确认第一版以当前店铺的经纬度作为周边推荐的查询中心，不以用户所在位置作为中心。
- 用户确认仅推荐与当前店铺同类型的店铺，以当前店铺的 typeId 作为筛选条件。
- 用户确认第一版查询半径为 5 公里，以当前店铺坐标为中心筛选范围内的同类型店铺。
- 用户确认周边推荐按与当前店铺的地理直线距离升序排列；距离相同时按店铺 ID 升序排列。
- 用户确认第一版提供“查看更多”入口。商详任务链聚合首屏周边推荐，查看更多通过独立查询接口继续浏览，仍以当前店铺为中心，沿用相同的范围、类型筛选和排序规则，不重新执行首屏任务链。
- 用户确认商详首次加载最多展示 6 家周边店铺，不足时展示实际结果。
- 查询结果排除当前店铺；展示距离表示推荐店铺与当前店铺之间的距离，使用“距该店”等明确文案。
- 周边查询依赖当前店铺的坐标，须在基础资料查询完成后执行；该查询按已确认规则作为可选节点处理。
- 商详周边推荐与既有基于用户定位的附近店铺列表是不同用例，既有列表的查询中心保持原约定。

### 未决问题

- 查看更多的分页或结果集上限及具体页面交互；已确认首次加载数量并提供查看更多入口。
- 当前店铺缺少有效坐标、无附近结果及查询失败时的具体展示与重试规则。
