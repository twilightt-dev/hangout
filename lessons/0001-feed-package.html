一篇博客，如何出现在粉丝的关注动态中？

本课的目标：沿着“发布”和“读取”两条流程，看懂 Feed 包中的七个文件。结束后，遇到配置、分页或推送问题，你能找到相应代码。

七个文件两条流程分页例子自测职责速查表
先记住三个存储位置

tb_blog 存博客内容；Redis feed:{userId} 存博客 ID 与发布时间；tb_feed_task 存待处理任务及进度。后台任务表和用户时间线是两种不同的数据。

七个文件各管一件事

① FeedProperties：配置

统一提供窗口天数、热点阈值、页大小、处理批大小和租约时间。其他类读取这些值，避免各处写死数字。

@ConfigurationProperties(prefix = "feed") 绑定配置。默认 30 天、1000 粉丝、每页 10 篇、每批 200 个、租约 300 秒；辅助方法限制配置范围。租约最低 30 秒在任务认领时保证。

② FeedRepository：业务数据查询

通过现有 BlogMapper 和 FollowMapper 查询博客和关注关系，提供“我关注谁”“作者是否热点”“下一批粉丝是谁”“这些 ID 对应哪些博客”。主键、批量 ID 与计数查询复用 MyBatis-Plus，自定义 SQL 放进对应 XML。

authors() 分类作者；recent() 查询时间范围内最近博客；history() 按博客 ID 分批扫描历史。粉丝数直接统计 tb_follow。

查看源码 · 博客 SQL · 关注 SQL

③ FeedCache：Redis 时间线操作

负责 ZSET 写入、候选 ID 读取、过期条目清理，以及重建状态。ZSET 只存 ID，内容仍由数据库补齐。

ready() 判断缓存是否可用；add() 写入 ID 和时间；candidates() 倒序取候选；invalidate() 使完成标记失效。

重建使用独立 token；complete() 的 Lua 比较 token 后原子写完成标记，避免旧请求覆盖后来的失效操作。

查看源码

④ FeedTimeline：排序与分页计算

这是不访问数据库或 Redis 的计算工具。把普通作者和热点作者的博客合并后，按 ID 去重，过滤时间范围，再排序分页。

score() 转 UTC 毫秒；time() 反向转换；page() 返回 list / minTime / offset。相同时间按 ID 字符串倒序，与 Redis 同分顺序一致。

⑤ FeedService：读取流程协调

关注动态接口的业务入口。校验登录和游标，分类作者，必要时重建普通作者缓存，查询热点作者博客，交给 Timeline 合并分页，再批量补作者昵称和头像。

cachedCandidates() 过滤已取关或不存在的博客，并继续扫描补足候选。Redis 路径失败时查数据库；数据库失败返回加载错误。

查看源码

⑥ FeedTaskRepository：任务持久化

通过 FeedTaskMapper 和对应 XML 操作 tb_feed_task。负责入队、查询到期任务、认领租约、保存进度、记录完成状态和安排重试。Repository 计算重试与租约时间，Mapper XML 执行 SQL。

publish() 入队发布任务；relationship() 入队关系维护任务；claim() 防止重复认领与旧快照推进；retry() 退避 2、4、8 秒，最多 300 秒。

查看源码 · 任务 SQL

⑦ FeedTaskWorker：后台执行

@Scheduled 默认启动 5 秒后开始，每次扫描结束后等 1 秒，再处理最多 20 个到期任务。先取得租约，再按任务类型执行业务。

PUBLISH 分批推送普通作者博客；BACKFILL 失效标记；CLEANUP 清理取关作者条目；RECLASSIFY 分批失效粉丝缓存。成功保存进度，失败交给 Repository 安排重试。

把文件放回真实流程

普通作者发布博客

BlogServiceImpl
同事务保存博客与任务→FeedTaskRepository
任务入队→FeedTaskWorker
提交后扫描、认领→FeedRepository
查博客与粉丝→FeedCache
写入粉丝时间线

每批成功后，Worker 通过 TaskRepository 保存最后一个粉丝 ID。重启后读取该检查点继续；失败的批次可能重复执行，重复 ZADD 同一个博客 ID 不会新增第二个成员。热点作者在消费时判断后跳过逐粉丝推送。

用户读取关注动态

BlogController→FeedService→FeedRepository
查询作者与分类→普通：FeedCache + 查内容
热点：数据库 recent()→FeedTimeline
去重、排序、分页

容易误读的地方：BACKFILL 当前只让重建标记失效；窗口内历史内容由下一次读取的 FeedService.ensureCache() 补齐。取关是否生效也由读取时过滤保证，后台清理可以稍后完成。

lastId 是时间，offset 是同时间内的位置

假设合并后有三篇博客，时间都为 T，ID 字符串顺序为 9 → 80 → 7，页大小为 2。

请求返回博客下次游标
lastId ≥ T，offset = 09、80lastId = T，offset = 2
lastId = T，offset = 27lastId = T，offset = 3
lastId = T，offset = 3空列表前端显示“已经到底啦~”

如果只记时间，下一页会再次遇到同时间的博客；offset 告诉 Timeline 已经跳过多少条。若下一页进入更早的时间，offset 改为该页尾部时间的条数。候选数先取 offset + pageSize，为跳过同分旧条目留出空间。
